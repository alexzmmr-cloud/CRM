# CRM-lite для агентства выставочных стендов

Короткое описание: система учёта и ведения входящих лидов из разных каналов (сайт, почта, телефон, рекомендации, ручной ввод) с последующей квалификацией, привязкой к компаниям и контактным лицам, фиксацией параметров проекта (бюджет, площадка, сроки, формат) и ведением сделок по воронке до закрытия (успех или отказ). Помогает менеджерам не терять заявки, отслеживать этапы сделок, контролировать задачи и дедлайны, видеть ответственных лиц у клиента и оценивать текущий объём потенциальной выручки в работе.

## Основные возможности

* Сущности: Lead, Account, Contact, Opportunity, Activity; стадии сделки (Stage) — не отдельная сущность БД, а зафиксированный в коде список значений с метаданными (порядок, признак "выиграна"/"проиграна", цвет)
* Списки сущностей — таблицы с поиском, фильтрами и зебра-подсветкой строк; карточки — на отдельных роутах `/leads/[id]`, `/accounts/[id]`, `/contacts/[id]`, `/opportunities/[id]`; создание записей — через модальные окна
* Вычисляемый статус сделки (Открыта/Выиграна/Проиграна) из стадии, плюс независимый флаг "Зависшая" (нет ни одной незавершённой задачи), сочетается с любым статусом
* Главная страница с KPI-снимком и графиками; отдельный экран Dashboard с показателями, диаграммами по стадиям сделок и статусам лидов, списками Recent Leads, Overdue Tasks и Stuck Deals

## Основной пользовательский сценарий

1. Пользователь запускает проект.
2. Подготавливает данные.
3. Создаёт лида в интерфейсе.
4. Конвертирует лида в контакт и компанию, при необходимости создаёт сделку.
5. Открывает карточки связанных сущностей и видит корректные связи.
6. Двигает сделку по воронке.
7. Добавляет заметку и задачу.
8. Проверяет поиск и фильтры.
9. Открывает отдельный Dashboard и видит показатели из текущего состояния базы.
10. Меняет лида или сделку и проверяет, что Dashboard обновился через повторный запрос.

## Стек и инструменты

* Next.js, React, TypeScript
* PostgreSQL
* Prisma — `prisma@6.19.3`, `@prisma/client@6.19.3` (стандартный контур Prisma 6: `DATABASE_URL` читается в `schema.prisma` через `env("DATABASE_URL")`; `@prisma/adapter-pg`, `PrismaPg` и `prisma.config.ts` не используются)
* Zod — валидация данных
* chart.js@4.5.1 и react-chartjs-2@5.3.1 — диаграммы на Dashboard

## Запуск

Общие шаги одинаковы для обеих ОС, отличается только способ поднять локальный PostgreSQL (шаг 1) — команды для него ниже, в разделах Mac OS и Windows.

1. Убедиться, что локальный PostgreSQL запущен и доступен.
2. Скопировать `.env.example` в `.env` и указать реальный `DATABASE_URL` (пользователь/пароль/база — свои).
3. Установить зависимости: `npm install`.
4. Применить миграции: `npx prisma migrate deploy` (или `npx prisma migrate dev` при разработке).
5. Заполнить БД dev-данными: `npm run db:seed`.
6. Запустить dev-сервер: `npm run dev` — приложение открывается на `http://localhost:3000`.

### Запуск PostgreSQL на Mac OS (Homebrew)

```bash
brew install postgresql@16
brew services start postgresql@16      # запустить как фоновый сервис
brew services stop postgresql@16       # остановить
brew services list                     # проверить статус
```

### Запуск PostgreSQL на Windows (установщик EDB)

1. Скачать и установить PostgreSQL с [postgresql.org/download/windows](https://www.postgresql.org/download/windows/) — установщик сам регистрирует службу Windows и запускает её после установки.
2. Дальше управлять службой можно через `services.msc` (найти `postgresql-x64-<версия>`) либо из терминала с правами администратора:

```powershell
net start postgresql-x64-16
net stop postgresql-x64-16
```

## Полезные команды

* `npm run dev` — запуск дев-сервера Next.js.
* `npm run build` / `npm run start` — production-сборка и запуск.
* `npm run lint` — проверка ESLint.
* `npm run db:seed` — заполнить текущую БД предсказуемым набором dev-данных (не удаляя существующие записи).
* `npm run db:reset` — полностью сбросить БД (`prisma migrate reset --force`), накатить миграции и seed заново; используется для восстановления чистого воспроизводимого состояния dev-данных.
* `npx prisma validate` — проверить корректность `schema.prisma`.
* `npx prisma migrate status` — проверить состояние миграций относительно БД.

## Демонстрационный сценарий и контрольные данные

После `npm run db:reset` (или `db:seed` на пустой БД) в базе гарантированно оказывается предсказуемый набор данных — на нём можно свериться, что всё поднялось корректно, до начала ручной проверки сценария.

**Контрольные цифры сразу после seed:**

* Leads — 6 записей: 3 уже конвертированы (`status: converted`, у каждого есть связанная сделка), 3 оставлены неконвертированными специально для ручной проверки convert lead — `Захарова Мария` (new), `Кузнецов Дмитрий` (new), `Петров Иван` (disqualified).
* Accounts — 4, Contacts — 5, Opportunities — 6, Activities — 11.
* Открытых сделок (стадии `new`/`qualified`/`proposal`/`negotiation`) — 4, сумма — 2 120 000 ₽ (250 000 + 600 000 + 420 000 + 850 000). Это число должно совпадать с KPI-карточкой "Сумма открытых сделок" на главной странице и на Dashboard сразу после seed.
* Won — 1 сделка ("Выставочный стенд БрендЗона Плюс", 300 000 ₽), Lost — 1 сделка ("Архивная сделка АртДизайн Групп", 180 000 ₽).
* Stuck Deals — 2 сделки без единой незавершённой задачи: "Выставочный стенд БрендЗона Плюс" (won) и "Стенд для СтройВыставка" (open, есть только уже выполненная задача).

**Проверка сценария (соответствует разделу «Основной пользовательский сценарий»):**

1. `npm run db:reset` → в консоли появляется лог seed-скрипта с итоговыми числами (Leads: 6, Accounts: 4, Contacts: 5, Opportunities: 6, Activities: 11) — сверить с числами выше.
2. Открыть `/leads`, найти лид `Захарова Мария` (source `site`, status `new`) → выполнить convert lead → должны появиться связанные Contact и Account с её именем/компанией.
3. Открыть карточку появившегося Contact → должна быть видна связь с Account и с исходным Lead.
4. Открыть `/opportunities`, найти "Стенд для ООО Экспо Стенд" (stage `negotiation`) → перевести в `won`, указав сумму и контакт → на карточке должна появиться дата закрытия (`closedAt`) и бейдж "Выиграна".
5. На карточке этой сделки добавить note и task с dueDate → оба должны появиться в списке активностей.
6. Открыть `/dashboard` → KPI и графики должны отражать уже изменённые данные (на одну сделку won больше, сумма открытых сделок уменьшилась на 850 000 ₽).
7. Открыть KPI-карточку Stuck Deals на Dashboard → клик должен вести на `/opportunities` с применённым фильтром "Зависшая".

## Изменение схемы данных

Любое изменение моделей вносится в `prisma/schema.prisma`, затем применяется командой `npx prisma migrate dev --name <короткое_имя>` — она создаёт новую миграцию в `prisma/migrations/` и применяет её к локальной БД. `db:reset` при необходимости восстанавливает базу с нуля (все миграции + seed) — это единственный предусмотренный способ отката к чистому dev-состоянию, отдельного механизма "rollback" миграции нет.

## Возможности для развития продукта

* Критерий «зависшей» сделки (Stuck) опирается на системную работу с клиентом — назначенные события (задачи), а не на срок сам по себе. Можно установить временную отсечку или дедлайн; для доработки потребуется отдельное поле срока (например, `stageChangedAt`) и расчёт критерия по времени.
* KPI-карточка «Просроченных задач» на Dashboard пока не кликабельна — в отличие от карточки «Зависших сделок», переход на отфильтрованный список сделок с просроченными задачами не реализован; по требованию заказчика возможна доработка.
