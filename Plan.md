# Plan.md: CRM-lite для агентства выставочных стендов

## 1. Текущий статус

- Приоритет: `P0`
- Основная цель: локально воспроизводимая CRM-lite (Next.js, React, TypeScript, PostgreSQL, Prisma, Zod) с полным основным пользовательским сценарием — от приёма лида до Dashboard.
- Обязательное ограничение: без авторизации и ролей (однопользовательский MVP); без Docker — локальный PostgreSQL подключается напрямую через `DATABASE_URL`. Backend — Server Actions (не Route Handlers).
- Основной контекст проекта: `README.md`.
- Секреты: `DATABASE_URL` не печатается, не коммитится, не вставляется в ответы ИИ; файл `.env` с реальным значением создаётся только локально и не коммитится; в репозитории — только `.env.example` без реальных значений.
- Статус: все запланированные шаги выполнены, проект готов к сдаче (см. раздел 6).

## 1.1 Целевой сценарий

Менеджер агентства должен пройти один основной маршрут:

1. Запускает проект локально (`npm run dev`, БД поднята и заполнена).
2. Подготавливает данные (seed или ручной ввод).
3. Создаёт лида в интерфейсе с указанием обязательного источника (`site`/`email`/`phone`/`referral`/`manual`).
4. Конвертирует лида в контакт и компанию, при необходимости — в сделку (упрощённый convert lead).
5. Открывает карточки связанных сущностей (лид, компания, контакт, сделка) и видит корректные связи между ними.
6. Двигает сделку по воронке стадий, включая переход в `won`/`lost`.
7. Добавляет заметку (note) и задачу (task) как Activity к сделке.
8. Проверяет поиск и фильтры по спискам сущностей.
9. Открывает отдельный Dashboard и видит KPI-карточки, диаграммы и summary из текущего состояния базы.
10. Меняет лида или сделку и проверяет, что Dashboard обновился через повторный запрос (без реалтайма/сокетов).

## 1.2 Что не входит в текущую версию

- Авторизация, роли, сессии, разграничение доступа.
- Docker/контейнеризация БД — только локальный PostgreSQL напрямую.
- Realtime-обновление Dashboard (веб-сокеты, polling) — только обновление через повторный запрос/навигацию.
- Удаление сущностей (только CRUD в объёме create/read/update).
- Множественные заметки с историей изменений — Activity фиксируется как список записей note/task, но без версионирования содержимого.
- Обратная конвертация сделки в лида.
- Пользовательская настройка стадий воронки через UI (стадии редактируются только на уровне кода/БД разработчиком, не конечным пользователем).
- Импорт/экспорт данных, интеграции с внешними каналами (реальная почта/телефония).
- Pagination с бесконечной прокруткой — списки выводятся полностью без лимита.
- Route Handlers/API-роуты как основной способ мутаций — используются Server Actions.

## 1.3 Допущения и решения

- Локальный PostgreSQL уже установлен и запущен, Docker не используется.
- Структура проекта — `create-next-app` в корне репозитория, App Router, без `src/`.
- Версии Prisma фиксируются точно: `prisma@6.19.3`, `@prisma/client@6.19.3`, стандартный контур (`env("DATABASE_URL")` в `schema.prisma`, без `@prisma/adapter-pg`/`PrismaPg`/`prisma.config.ts`).
- `chart.js@4.5.1` и `react-chartjs-2@5.3.1` устанавливаются точными версиями (`--save-exact`) для диаграмм Dashboard.
- Lead.status: `new` → `converted`/`disqualified`; после `converted` лид считается неизменяемым источником для связанной сделки.
- Opportunity.stage: `new` → `qualified` → `proposal` → `negotiation` → `won`/`lost`; `Stage` — allowlist-модуль в коде (`lib/opportunity.ts`, `OPPORTUNITY_STAGE_META` с порядком/`isWon`/`isLost`/цветом), не отдельная таблица БД — стадии не редактируются пользователем через UI, поэтому таблица не даёт функционального выигрыша.
- Пагинация в списках сущностей не нужна для этого MVP — списки выводятся полностью без лимита.
- Convert lead: маппинг `Lead.contact` → `Contact.email`/`Contact.phone` определяется по формату значения (есть `@` → `email`, иначе → `phone`).
- Convert lead идемпотентен: повторный вызов для уже `converted` лида возвращает существующую связанную `Opportunity`, не создаёт дубли.
- Переход `Opportunity.stage` в `won` требует заполненных `amount` и `contactId`; переход в `lost` требует причину расторжения, сохраняемую как `Activity` типа `note` — правило срабатывает только на факте перехода в новую стадию, не при повторном сохранении уже `won`/`lost` сделки.
- Переход `Opportunity.stage` в `won`/`lost` разрешён из любой стадии, без последовательного прохождения промежуточных стадий. При переходе в `won`/`lost` автоматически проставляется `Opportunity.closedAt`; при обратном переходе в открытую стадию — сбрасывается.
- Сделка редактируется (включая смену stage) без ограничений и после перехода в `won`/`lost`.
- Состав фильтров: Leads — поиск по имени/компании + фильтры по source и status; Opportunities — поиск по названию + фильтры по stage и статусу (Открыта/Выиграна/Проиграна/Зависшая); Accounts/Contacts — поиск по имени.
- Статус сделки (Открыта/Выиграна/Проиграна) — вычисляемый признак из `stage`, не отдельное поле в БД. «Зависшая» — независимый флаг (нет ни одной незавершённой задачи), может сочетаться с любым базовым статусом: пост-продажные задачи (поздравления, напоминания о повторной продаже) тоже нуждаются в отслеживании после `won`/`lost`. Критерий не учитывает срок задачи — ограничение зафиксировано в README, раздел «Возможности для развития продукта».
- Master-detail — отдельные динамические роуты (`/leads/[id]` и аналогично для остальных сущностей), не query-параметры на одной странице.
- Создание записи — только через модальное окно по кнопке в шапке списка; отдельных страниц вида `/leads/new` нет.
- Быстрые действия (предзаполнение формы создания сделки компанией/контактом) — через пропсы модального компонента, не через query-параметры.

## 2. Требования к результату

- Next.js + React + TypeScript, App Router, без `src/`.
- PostgreSQL как единственная БД, подключение через `DATABASE_URL` в `.env`, `.env.example` — без секретов.
- Prisma `6.19.3` (client и CLI), стандартный контур без адаптеров.
- Zod — валидация входных данных на границе (формы/server actions).
- `chart.js@4.5.1` + `react-chartjs-2@5.3.1` — точные версии для диаграмм Dashboard.
- Все данные читаются и пишутся через Prisma, без моков и захардкоженных данных в интерфейсе.
- Все обязательные сущности реализованы: Lead, Account, Contact, Opportunity, Activity.
- Основной пользовательский сценарий (раздел 1.1) проходим целиком вручную без ошибок.
- Dashboard показывает реальные агрегаты из БД (не статичные числа), обновляется по повторному запросу после изменения данных.
- Backend — Server Actions.
- Можно менять: `app/`, `lib/`, `prisma/`, `package.json`, `README.md`, этот файл.
- Нельзя добавлять функциональность сверх раздела 1.2 без отдельного согласования с пользователем.

## 2.1 Раскладка по слоям

### Frontend

- Next.js App Router: главная (`/`) с кратким KPI-снимком, страницы списков (`<table>` с колонками) и карточек `/leads`, `/accounts`, `/contacts`, `/opportunities`.
- Master-detail через отдельные динамические роуты `/[entity]/[id]` со связями (лид → контакт/компания/сделка, сделка → активности).
- Формы создания/редактирования (CRUD) для Lead, Account, Contact, Opportunity — создание через модальные окна, редактирование прямо на карточке (горизонтальный grid, форма всегда открыта).
- Компонент воронки сделок (Stage) с быстрым переключением стадии.
- Быстрые действия: создать сделку (с предзаполнением компании/контакта), сменить стадию, добавить note, добавить task, выполнить convert lead, создать контакт для компании.
- Поиск и фильтры в списках, плюс глобальный debounced-поиск в навигации.
- Единая `.card` дизайн-система (`.card-header`/`.card-title`/`.card-body`), списки как таблицы с мягкой зебра-подсветкой строк.
- Отдельный экран `/dashboard`: KPI-карточки (с sub-текстом и акцентами при тревожных значениях), две диаграммы (Chart.js) по стадиям сделок и статусам лидов, summary по статусам и источникам лидов, списки Recent Leads, Overdue Tasks и Stuck Deals (кликабельная карточка с переходом на отфильтрованный список).

### Backend

- Server Actions/Server Components для CRUD Lead, Account, Contact, Opportunity, Activity.
- Валидация входных данных через Zod перед записью в БД.
- Функция convert lead — атомарная транзакция (Lead → Contact + Account (+ Opportunity)), идемпотентна.
- Функции агрегации для Dashboard (группировки по stage/status/source, подсчёт просроченных задач, сумма открытых сделок) — только на сервере, без Prisma-запросов в клиентских компонентах.
- Allowlist-модули для `Lead.status`, `Opportunity.stage`, `Lead.source`, `Activity.type` — единая точка правды для допустимых значений, подписей и стилей, переиспользуемая в валидации и UI.

### Database

- `Lead`: id, name, company, contact, note, source, status, createdAt, updatedAt;
- `Account`: id, name, website, industry, phone, createdAt, updatedAt;
- `Contact`: id, name, email, phone, role, accountId, createdAt, updatedAt;
- `Opportunity`: id, title, amount, venue, timeline, format, stage, closedAt, accountId, contactId, leadId, createdAt, updatedAt;
- `Activity`: id, type, content, dueDate, done, opportunityId, createdAt;

- статусы Lead: `new`, `converted`, `disqualified`;
- источники Lead: `site`, `email`, `phone`, `referral`, `manual`;
- стадии Opportunity: `new`, `qualified`, `proposal`, `negotiation`, `won`, `lost` (allowlist в коде, не таблица БД);
- типы Activity: `note`, `task`;
- связи: `Account -> Contact[]`, `Account -> Opportunity[]`, `Contact -> Opportunity[]`, `Lead -> Opportunity?` (1:1, `leadId` unique), `Opportunity -> Activity[]`;
- `Activity.dueDate`/`Activity.done` заполняются только для `type = "task"`, для `type = "note"` не используются (значение `null`).
