# Plan.md: CRM-lite для агентства выставочных стендов

## 1. Текущий статус

- Приоритет: `P0`
- Текущее состояние: план зафиксирован, кода нет — проект стартует с нуля.
- Основная цель цикла: собрать локально воспроизводимую CRM-lite (Next.js, React, TypeScript, PostgreSQL, Prisma, Zod) с полным основным пользовательским сценарием — от приёма лида до Dashboard.
- Обязательное ограничение: без авторизации и ролей (однопользовательский MVP); без Docker — локальный PostgreSQL подключается напрямую через `DATABASE_URL`.
- Основной контекст проекта: `README.md`.
- Секреты: `DATABASE_URL` не печатается, не коммитится, не вставляется в ответы ИИ; файл `.env` с реальным значением создаётся только локально и не коммитится (уже исключён в `.gitignore`); в репозитории — только `.env.example` без реальных значений.
- Сейчас в работе: Фаза 1 — зафиксировать легенду, границу MVP и план (этот документ).

## 1.1 Целевой сценарий

Менеджер агентства должен пройти один основной маршрут:

1. Запускает проект локально (`npm run dev`, БД поднята и заполнена).
2. Подготавливает данные (seed или ручной ввод).
3. Создаёт лида в интерфейсе с указанием обязательного источника (`site`/`email`/`phone`/`referral`/`manual`).
4. Конвертирует лида в контакт и компанию, при необходимости — в сделку (упрощённый convert lead).
5. Открывает карточки связанных сущностей (лид, компания, контакт, сделка) и видит корректные связи между ними.
6. Двигает сделку по воронке стадий, включая переход в `won`/`lost`.
7. Добавляет заметку (note) и задачу (task) как Activity к сделке.
8. Проверяет поиск и фильтры по спискам сущностей.
9. Открывает отдельный Dashboard и видит KPI-карточки, диаграммы и summary из текущего состояния базы.
10. Меняет лида или сделку и проверяет, что Dashboard обновился через повторный запрос (без реалтайма/сокетов).

## 1.2 Что не входит в текущую версию

- Авторизация, роли, сессии, разграничение доступа.
- Docker/контейнеризация БД — только локальный PostgreSQL напрямую.
- Realtime-обновление Dashboard (веб-сокеты, polling) — только обновление через повторный запрос/навигацию.
- Удаление сущностей (только CRUD в объёме create/read/update, если не решено иное на шаге проектирования backend).
- Множественные заметки с историей изменений — Activity фиксируется как список записей note/task, но без версионирования содержимого.
- Обратная конвертация сделки в лида.
- Настраиваемые пользователем стадии воронки (Stage — фиксированный allowlist в коде, не редактируется через UI).
- Импорт/экспорт данных, интеграции с внешними каналами (реальная почта/телефония).
- Pagination с бесконечной прокруткой — если потребуется постраничность, будет простой вариант (см. открытые вопросы).

## 1.3 Допущения и открытые вопросы

### Допущения

- Локальный PostgreSQL уже установлен и запущен, Docker не используется.
- Структура проекта — `create-next-app` в корне репозитория, App Router, без `src/`.
- `Stage` — allowlist в коде (константы допустимых значений stage и их подписи в отдельном модуле), не отдельная таблица БД.
- Версии Prisma фиксируются точно: `prisma@6.19.3`, `@prisma/client@6.19.3`, стандартный контур (`env("DATABASE_URL")` в `schema.prisma`, без `@prisma/adapter-pg`/`PrismaPg`/`prisma.config.ts`).
- `chart.js@4.5.1` и `react-chartjs-2@5.3.1` устанавливаются точными версиями (`--save-exact`) для диаграмм Dashboard.
- Lead.status: `new` → `converted`/`disqualified`; после `converted` лид считается неизменяемым источником для связанной сделки.
- Opportunity.stage: `new` → `qualified` → `proposal` → `negotiation` → `won`/`lost`.
- Пагинация в списках сущностей не нужна для этого MVP — списки выводятся полностью без лимита.

### Вопросы, которые нельзя восстановить из входа

- Правила переходов сделки в `won`/`lost` — можно ли переходить в `won`/`lost` из любой промежуточной стадии, или только последовательно — требует уточнения на шаге реализации воронки (Фаза 7).
- Можно ли редактировать сделку после перехода в `won`/`lost` (например, менять stage обратно) — требует уточнения на Фазе 7.
- Точный маппинг полей при convert lead (что из `Lead.contact` идёт в `Contact.email` или `Contact.phone`, если поле одно и то же) — требует уточнения на Фазе 6.
- Состав и точные формулировки фильтров (по каким полям фильтруются лиды/сделки) — требует уточнения на Фазе 5.
- "Stuck Deals" на Dashboard — опционально, критерий "зависшей" сделки (например, N дней без изменения стадии) не определён — требует уточнения на Фазе 8.

## 2. Требования к результату

- Next.js + React + TypeScript, App Router, без `src/`.
- PostgreSQL как единственная БД, подключение через `DATABASE_URL` в `.env`, `.env.example` — без секретов.
- Prisma `6.19.3` (client и CLI), стандартный контур без адаптеров.
- Zod — валидация входных данных на границе (формы/server actions).
- `chart.js@4.5.1` + `react-chartjs-2@5.3.1` — точные версии для диаграмм Dashboard.
- Все данные читаются и пишутся через Prisma, без моков и захардкоженных данных в интерфейсе.
- Все обязательные сущности из README реализованы: Lead, Account, Contact, Opportunity, Activity (Stage — allowlist в коде).
- Основной пользовательский сценарий (раздел 1.1) проходим целиком вручную без ошибок.
- Dashboard показывает реальные агрегаты из БД (не статичные числа), обновляется по повторному запросу после изменения данных.
- Можно менять: `app/`, `lib/`, `prisma/`, `package.json`, `README.md`, `Plan.md`.
- Нельзя добавлять функциональность сверх раздела 1.2 без отдельного согласования с пользователем.

## 2.1 Раскладка по слоям

### Frontend

- Next.js App Router, страницы списков и карточек: `/leads`, `/accounts` (или объединённо с контактами), `/contacts`, `/opportunities`.
- Master-detail интерфейс для карточек сущностей со связями (лид → контакт/компания/сделка, сделка → активности).
- Формы создания/редактирования (CRUD) для Lead, Account, Contact, Opportunity.
- Компонент воронки сделок (Stage) с быстрым переключением стадии.
- Быстрые действия: создать сделку, сменить стадию, добавить note, добавить task, выполнить convert lead.
- Поиск и фильтры в списках.
- Отдельный экран `/dashboard`: KPI-карточки, две диаграммы (Chart.js) по стадиям сделок и статусам лидов, summary по статусам и источникам лидов, списки Recent Leads и Overdue Tasks (Stuck Deals — опционально).

### Backend

- Server Actions/Server Components для CRUD Lead, Account, Contact, Opportunity, Activity.
- Валидация входных данных через Zod перед записью в БД.
- Функция convert lead — атомарная транзакция (Lead → Contact + Account (+ Opportunity)), идемпотентность — требует уточнения на Фазе 6.
- Функции агрегации для Dashboard (группировки по stage/status/source, подсчёт просроченных задач, сумма открытых сделок) — только на сервере, без Prisma-запросов в клиентских компонентах.
- Allowlist-модули в коде для `Lead.status`, `Opportunity.stage`, `Lead.source`, `Activity.type` — единая точка правды для допустимых значений, подписей и стилей, переиспользуемая в валидации и UI.

### Database

- `Lead`: id, name, company, contact, note, source, status, createdAt, updatedAt;
- `Account`: id, name, website, createdAt, updatedAt;
- `Contact`: id, name, email, phone, role, accountId, createdAt, updatedAt;
- `Opportunity`: id, title, amount, venue, timeline, format, stage, accountId, contactId, leadId, createdAt, updatedAt;
- `Activity`: id, type, content, dueDate, done, opportunityId, createdAt;

- статусы Lead: `new`, `converted`, `disqualified`;
- источники Lead: `site`, `email`, `phone`, `referral`, `manual`;
- стадии Opportunity: `new`, `qualified`, `proposal`, `negotiation`, `won`, `lost`;
- типы Activity: `note`, `task`;
- связи: `Account -> Contact[]`, `Account -> Opportunity[]`, `Contact -> Opportunity[]`, `Lead -> Opportunity?` (1:1, `leadId` unique), `Opportunity -> Activity[]`;

- `Activity.dueDate`/`Activity.done` заполняются только для `type = "task"`, для `type = "note"` не используются (значение `null`) — точный механизм ограничения (application-level vs схема) решается на Фазе 3;
- переходы `Opportunity.stage` в `won`/`lost` — правило фиксируется на Фазе 7 (открытый вопрос 1.3).
